## ADDED Requirements

### Requirement: Запуск массовой рассылки уведомлений

Система SHALL предоставлять HTTP-эндпоинт `POST /api/v1/notifications`, принимающий канал доставки (`sms` или `email`), приоритет (`transactional` или `marketing`, по умолчанию `marketing`), текст сообщения и массив получателей в формате `{ id, address }`. На успешный приём система MUST вернуть HTTP 202 с идентификатором batch и количеством принятых сообщений, а также MUST создать в базе данных запись batch и по одной записи `notification` в статусе `queued` на каждого получателя.

#### Scenario: Успешный приём bulk-запроса
- **WHEN** клиент отправляет валидный `POST /api/v1/notifications` с заголовком `Idempotency-Key` и двумя получателями
- **THEN** ответ имеет статус 202, тело содержит `batch_id` и `accepted=2`, в БД создан 1 batch и 2 уведомления со статусом `queued`, и в брокер сообщений опубликовано 2 задачи в очередь, соответствующую приоритету

#### Scenario: Невалидный канал
- **WHEN** клиент отправляет запрос с `channel="fax"`
- **THEN** ответ имеет статус 422 и ни одна запись в БД не создаётся

#### Scenario: Пустой массив получателей
- **WHEN** клиент отправляет запрос с `recipients=[]`
- **THEN** ответ имеет статус 422

#### Scenario: Отсутствует Idempotency-Key
- **WHEN** клиент отправляет валидный запрос без заголовка `Idempotency-Key`
- **THEN** ответ имеет статус 400 и ни одна запись в БД не создаётся

### Requirement: Получение истории и статусов по подписчику

Система SHALL предоставлять HTTP-эндпоинт `GET /api/v1/subscribers/{id}/notifications`, возвращающий список уведомлений конкретного подписчика с текущим статусом каждого, отсортированный по убыванию `created_at`, с поддержкой пагинации и опциональных фильтров `status`, `channel`. Каждое уведомление в ответе MUST содержать `id`, `channel`, `priority`, `status`, `created_at`, `sent_at`, `delivered_at`, `failed_at`, `last_error`.

#### Scenario: Получение списка
- **WHEN** для подписчика `42` существуют 3 уведомления в разных статусах
- **THEN** `GET /api/v1/subscribers/42/notifications` возвращает 3 элемента с актуальными статусами и таймстампами

#### Scenario: Фильтр по статусу
- **WHEN** клиент запрашивает `GET /api/v1/subscribers/42/notifications?status=delivered`
- **THEN** в ответе только уведомления со статусом `delivered`

#### Scenario: Несуществующий подписчик
- **WHEN** для подписчика `9999` нет ни одного уведомления
- **THEN** ответ имеет статус 200 и пустой список

### Requirement: OpenAPI-документация

Система SHALL публиковать OpenAPI-схему по адресу `/docs/api` и интерактивную документацию для тестирования эндпоинтов API.

#### Scenario: Доступ к документации
- **WHEN** клиент открывает `/docs/api`
- **THEN** возвращается HTML-страница со Swagger/Scramble UI, содержащая описание всех публичных эндпоинтов v1
