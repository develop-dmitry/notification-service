### Requirement: Идемпотентность входящего API

Система SHALL требовать заголовок `Idempotency-Key` (UUID) для эндпоинта `POST /api/v1/notifications`. Повторный запрос с тем же ключом и идентичным телом в течение 24 часов MUST возвращать сохранённый ответ исходного запроса без создания новых уведомлений и без публикации новых задач в брокер.

#### Scenario: Повтор того же запроса
- **WHEN** клиент отправляет `POST /api/v1/notifications` с `Idempotency-Key: K`, получает ответ с `batch_id=B`, затем повторяет тот же запрос с тем же `K`
- **THEN** ответ имеет статус 202 с `batch_id=B`, в БД остаётся ровно один batch и исходный набор уведомлений, новые задачи в очередь не публикуются

#### Scenario: Конфликт тела при том же ключе
- **WHEN** клиент повторяет запрос с тем же `Idempotency-Key`, но изменённым телом
- **THEN** ответ имеет статус 409

#### Scenario: TTL ключа истёк
- **WHEN** прошло более 24 часов с момента первого запроса с ключом `K`, и клиент отправляет новый запрос с тем же `K`
- **THEN** запрос обрабатывается как новый, создаётся новый batch

### Requirement: Идемпотентность обработки задач воркером

Система SHALL гарантировать, что повторная доставка одной и той же задачи из брокера не приведёт к повторному вызову провайдера. Воркер MUST блокировать запись уведомления (SELECT FOR UPDATE) и пропускать обработку, если текущий статус не равен `queued`.

#### Scenario: Повторная доставка уже отправленного уведомления
- **WHEN** воркер получает задачу для уведомления, которое уже в статусе `sent`
- **THEN** воркер не вызывает провайдера, подтверждает сообщение брокеру и завершает обработку без изменений данных
